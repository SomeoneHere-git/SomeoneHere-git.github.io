## 1. Реалізація програмного модуля

На основі UML-моделі системи автентифікації було створено програмний модуль `AuthService` мовою C# (.NET).

Модуль містить 4 ключових методи з нетривіальною логікою (наявні умовні конструкції, обробка виняткових ситуацій та хэшування):

1. **`Register`** — реєстрація нового користувача з перевіркою довжини пароля (менше 6 символів викликає `ArgumentException`) та перевіркою на дублікат Email у базі даних (викликає `InvalidOperationException`).
2. **`Authenticate`** — авторизація користувача. Перевіряє наявність користувача в системі, порівнює хэші паролів і генерує сесійний токен безпеки `AuthToken`.
3. **`ValidateToken`** — валідація токена доступу. Містить логіку перевірки часу життя токена (`ExpiresAt`) порівняно з поточним часом (`DateTime.UtcNow`). Якщо токен застарів, він видаляється з активних.
4. **`HashPassword`** — хэшування паролів за алгоритмом SHA-256. Має умову повернення порожнього рядка при передачі порожнього пароля для запобігання помилкам.

## 2. Проєктування тестів (Класи еквівалентності та граничні значення)

Для кожного методу були визначені класи еквівалентності (EP) та граничні значення (BVA).

| Метод | Вхідні параметри | Клас еквівалентності (EP) / Граничне значення (BVA) | Очікуваний результат | Тип тесту |
| :--- | :--- | :--- | :--- | :--- |
| `Register` | Новий користувач | **EP:** Пароль містить 6 або більше символів | Успішна реєстрація (повертає `User`) | Позитивний |
| `Register` | Користувач вже існує | **EP:** Дублікат email у базі даних | Помилка `InvalidOperationException` | Негативний |
| `Register` | Коротка довжина пароля | **BVA:** Пароль довжиною 5 символів (нижче границі 6) | Помилка `ArgumentException` | Негативний |
| `Authenticate` | Коректні дані | **EP:** Існуючий email та правильний пароль | Успішна авторизація (повертає `AuthToken`) | Позитивний |
| `Authenticate` | Неіснуючий користувач | **EP:** Email відсутній у базі даних | Помилка `InvalidOperationException` | Негативний |
| `Authenticate` | Невірний пароль | **EP:** Спроба входу з неправильним паролем | Помилка `UnauthorizedAccessException` | Негативний |
| `ValidateToken` | Дійсний токен | **BVA:** Час дії `ExpiresAt` більший за поточний | Повертає `true` | Позитивний |
| `ValidateToken` | Прострочений токен | **BVA:** Час дії `ExpiresAt` менший або дорівнює поточному | Повертає `false` | Негативний |
| `HashPassword` | Будь-який рядок | **EP:** Коректне текстове значення пароля | Повертає SHA-256 хэш (64 символи) | Позитивний |
| `HashPassword` | Порожній рядок | **BVA:** Передача `""` або `null` (границя пустого поля) | Повертає порожній рядок `""` | Позитивний |

## 3. Набір модульних тестів (Патерн AAA)

Для тестування було використано сучасний фреймворк тестування `xUnit`. Усі модульні тести спроєктовано та написано суворо за патерном AAA (Arrange — Act — Assert).

Приклад одного з реалізованих тестів із коментарями та зазначенням застосованої техніки:

```csharp
[Fact(DisplayName = "Register: Помилка, якщо довжина пароля рівно 5 символів")]
public void Register_PasswordExactly5Chars_ThrowsArgumentException()
{
    // Техніка: BVA (Граничні значення), Негативний тест
    
    // Arrange (Підготовка оточення та вхідних даних)
    string email = "boundary@example.com";
    string shortPassword = "12345"; // Границя: рівно 5 символів (менше дозволених 6)

    // Act & Assert (Виконання дії та Перевірка очікуваного виключення)
    Assert.Throws<ArgumentException>(() => _authService.Register(email, shortPassword));
}
```

## 7. Бонус: Налаштування автоматизації через GitHub Actions

Для забезпечення практик безперервної інтеграції (CI) було налаштовано автоматичний запуск створеного набору модульних тестів при кожному оновленні коду в репозиторії.

У колі засобів автоматизації GitHub було створено конфігураційний файл `.github/workflows/dotnet.yml`, який описує такі кроки пайплайну:
1. Автоматичне розгортання віртуального середовища на базі ОС Ubuntu.
2. Ініціалізація та налаштування середовища виконання `.NET SDK 10.0`.
3. Відновлення залежностей проєкту (`dotnet restore`).
4. Компіляція та збірка рішення в конфігурації Release (`dotnet build`).
5. Прогін усього набору тестів `xUnit` із автоматичним збором аналітики покриття `Coverlet`.

*Результат:* Пайплайн успішно проходить у автоматичному режимі (статус: **Green Build**), що гарантує стабільність коду системи автентифікації при подальшій розробці.

## Висновки

Під час виконання лабораторної роботи було детально вивчено та практично застосовано методи модульного тестування (Unit Testing) програмного забезпечення на прикладі системи автентифікації користувачів (`AuthService`) мовою C# (.NET).

**Аналіз отриманих результатів покриття:**
* Завдяки комплексному застосуванню технік тест-дизайну — еквівалентного розбиття (EP) та аналізу граничних значень (BVA) — на етапі проєктування тестів, було створено оптимальний набір із 10 тест-кейсів.
* За допомогою утиліти `Coverlet` було згенеровано звіт покриття коду, який продемонстрував **100.0% Line Coverage** (покриття рядків) та **100.0% Branch Coverage** (покриття розгалужень), що значно перевищує встановлений інструкцією кваліфікаційний мінімум у 80%. Це свідчить про те, що кожна логічна гілка умовних операторів та блоки обробки винятків (`ArgumentException`, `InvalidOperationException` тощо) були успішно виконанні й перевірені під час тестів.

**Виявлені проблеми та шляхи поліпшення:**
1. *Попередження компілятора (Nullable Warnings):* Під час збірки проєкту та прогону тестів у консолі було зафіксовано попередження компілятора типу `CS818` та `CS8600`, які пов'язані з механізмом Nullable Reference Types у .NET 10 (попередження про можливість виникнення `null` у властивостях `Token`, `Email`, `PasswordHash`).
   * *Шлях поліпшення:* У подальшому рекомендується впровадити модифікатор `required` для моделей даних або явно ініціалізувати рядкові властивості за замовчуванням (`= string.Empty;`), щоб повністю усунути потенційні ризики виникнення `NullReferenceException` на етапі компіляції.
2. *Масштабованість тестування:* Для методів хэшування та валідації параметрів було використано поодинокі факти (`[Fact]`). При розширенні логіки це може призвести до дублювання коду тестів.
   * *Шлях поліпшення:* Доцільно перевести частину тестів на параметризовані тести (`[Theory]` та `[InlineData]` в xUnit), що дозволить виконувати один і той самий тестовий метод із різними наборами вхідних даних (наприклад, перевіряти кілька різних варіантів коротких паролів чи некоректних Email).

**Автоматизація (CI/CD):**
Додатково налаштований пайплайн у `GitHub Actions` успішно автоматизував процес збірки проєкту та виконання тестів при кожному оновленні гілки `lab3-testing`. Це дозволяє виявляти дефекти (регресійні помилки) на найранніших етапах розробки та гарантує, що працездатність та покриття сервісу автентифікації не впадуть нижче встановленого порогу якості при подальших комiтах.
