## 4. Результати рефакторингу власного коду

### Операція 1: Інкапсуляція даних у класі `Task`
**БУЛО (фрагмент `task.h`):**
```cpp
public:
    std::string taskId;
    std::string title;
    TaskStatus  status;
    std::string assigneeId;
```
**СТАЛО (фрагмент `task.h`):**
```cpp
private:
    std::string taskId;
    std::string title;
    TaskStatus  status;
    std::string assigneeId;

public:
    // Getters
    [[nodiscard]] std::string getTaskId() const { return taskId; }
    [[nodiscard]] std::string getTitle() const { return title; }
    [[nodiscard]] TaskStatus getStatus() const { return status; }
```
**ЧОМУ (обґрунтування):** Публічні поля класу порушують один із головних принципів ООП — інкапсуляцію. Якщо залишити поля публічними, інші частини програми зможуть змінити стан об'єкта (наприклад, встановити недопустимий статус) в обхід передбаченої логіки (`updateProgress`). Створення `private` полів із відповідними `getters` забезпечує безпеку та цілісність даних об'єкта.

### Операція 2: Оптимізація ініціалізації в конструкторі `Task`
**БУЛО (фрагмент `task.cpp`):**
```cpp
Task::Task(const std::string& taskId, const std::string& title, const std::string& assigneeId)
{
    if (taskId.empty()) { ... }
    if (title.empty()) { ... }
    this->taskId     = taskId;
    this->title      = title;
    this->assigneeId = assigneeId;
    this->status     = TaskStatus::TODO;
}
```
**СТАЛО (фрагмент `task.cpp`):**
```cpp
Task::Task(const std::string& taskId, const std::string& title, const std::string& assigneeId)
    : taskId(taskId), title(title), status(TaskStatus::TODO), assigneeId(assigneeId)
{
    if (taskId.empty()) { ... }
    if (title.empty()) { ... }
}
```
**ЧОМУ (обґрунтування):** В попередньому варіанті для типу `std::string` спочатку викликався конструктор за замовчуванням (який створював порожній рядок), а потім в тілі конструктора виконувалося присвоювання за допомогою `operator=`. Це призводить до подвійної роботи та зайвих витрат пам'яті/часу. Використання *member initializer list* ініціалізує змінні одразу необхідними значеннями.

### Операція 3: Оптимізація повернення масиву в `Team`
**БУЛО (фрагмент `team.cpp`):**
```cpp
std::vector<std::string> Team::getMembers() const
{
    return memberIds;
}
```
**СТАЛО (фрагмент `team.cpp`):**
```cpp
const std::vector<std::string>& Team::getMembers() const
{
    return memberIds;
}
```
**ЧОМУ (обґрунтування):** Оригінальний метод повертав `std::vector` по значенню, що викликало повне глибинне копіювання всього масиву з усіма його рядками при кожному виклику методу. Це є неефективним з точки зору пам'яті та процесора. Повертаючи масив за константним посиланням (`const reference`), ми уникаємо копіювання і при цьому гарантуємо, що клієнтський код не зможе змінити цей масив, зберігши безпеку.

## 7. Підсумкова рефлексія
Найціннішим досвідом під час виконання цього завдання було усвідомлення того, як навіть "працюючий" код може бути неефективним або небезпечним для підтримки. Процес Code Review навчив мене дивитися на код не лише з позиції "чи виконує він задачу", але й "наскільки він надійний та ефективний". Я зрозумів(-ла) важливість інкапсуляції, списків ініціалізації та правильної передачі складних об'єктів (наприклад, `std::vector`), що дозволить уникати типових помилок при написанні власного коду в майбутньому. Крім того, навичка покрокового рефакторингу із запуском регресійних тестів (Green State) додає впевненості у тому, що внесені зміни нічого не зламали.
